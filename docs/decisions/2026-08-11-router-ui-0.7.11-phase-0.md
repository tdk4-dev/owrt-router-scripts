## Release framing

**Release goal:** ship `0.7.11` only as the immutable trust/update bridge from
legacy Router UI installations to updater protocol 2, signed manifests,
transactional updates, exact rollback, and the future `0.8.x` line.

**Acceptance criteria closed by this decision package:** release scope is made
reviewable under source control; the next candidate identity is reserved;
adopted-overlay controls and fail-closed states are explicit; intended variants
and deliverables are declared; and the governance-to-implementation order is
fixed.

**Why the release cannot ship safely without this decision:** the two different
RC6 source trees used one visible RC/package identity, the proposed scope was
untracked in the primary checkout, and the exact accepted behavior and variant
set were not yet canonical. Building another candidate before resolving those
facts would permit evidence transfer, silent variant omission, or scope drift.

**Tests and evidence required later:** this Phase 0 record authorizes no product
tests. The future RC7 work must add the transition, state/control, exact-byte,
variant, VM, Factory, hardware, and publication evidence named below and in the
canonical scope.

## Decision 2: adopted-overlay compatibility acceptance

Full controls on a healthy adopted Xray overlay are retained in `0.7.11` as a
narrow regression repair. This restores the panel workflows expected for an
otherwise healthy configuration; it does not authorize new VPN capabilities
or any `0.8` feature.

A configuration is **healthy adopted** only when ownership metadata is valid,
the live Xray hash and supported structure match the adopted contract, no
drift or recovery condition exists, reboot validation is committed, no
mutation transaction is pending, and the caller has mutating authorization.
Failure of any precondition selects a fail-closed state.

In the matrix, **enabled** means the control may dispatch only its existing
bounded workflow after all preconditions pass. **Blocked** means it must not
dispatch a mutation or persist state; read-only status and diagnostics may
still render.

| Control family | Healthy adopted | Adoption required | Drift / recovery | Reboot pending | Read-only caller |
|---|---|---|---|---|---|
| Global VPN enable/disable | Enabled | Blocked | Blocked | Blocked | Blocked |
| Profiles: add, select/use, delete | Enabled | Blocked | Blocked | Blocked | Blocked |
| Subscriptions: import, sync, delete | Enabled | Blocked | Blocked | Blocked | Blocked |
| Ping refresh | Enabled | Blocked | Blocked | Blocked | Blocked |
| Automatic switching settings/actions | Enabled | Blocked | Blocked | Blocked | Blocked |
| Direct-domain and direct-IP rules | Enabled | Blocked | Blocked | Blocked | Blocked |
| Device VPN controls | Enabled | Blocked | Blocked | Blocked | Blocked |

Adoption preview remains read-only. Adoption confirmation is a separate,
explicit authenticated transition and must be blocked during drift/recovery,
reboot-pending, or read-only states. It must not silently normalize, adopt, or
rewrite an unsupported or ambiguous configuration.

Every future enabled mutation requires tests for exclusive serialization,
live-hash recheck immediately before persistence, bounded supported-field
changes, exact preimages, deterministic recovery, exact rollback/restoration,
Xray validation, and preservation of management-route and Tailscale
invariants. Browser evidence must cover rendering, enabled state, dispatch,
backend result, restoration, and console errors for every matrix state.

implicit defer. A deferred variant cannot be added later to the same immutable
tag or release.

## Decision 4: non-goals

Router UI `0.7.11` remains a bridge and regression-repair release. It must not
include:

- Router UI `0.8` navigation or page architecture;
- new product pages or new onboarding/setup flows;
- dynamic AdGuard installation;
- broad localization, mobile, visual, or navigation redesign;
- new VPN capabilities beyond restoring the declared existing panel controls;
- new hardware profiles without separate scope and evidence;
- new package categories or Factory capabilities beyond schema-2 release
  contracts for the declared variants;
- unrelated dependency, feed, or toolchain upgrades;
- opportunistic cleanup, refactoring, or performance work without a release
  blocker and explicit acceptance threshold.
