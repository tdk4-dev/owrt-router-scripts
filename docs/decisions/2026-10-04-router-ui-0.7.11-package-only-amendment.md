# Router UI 0.7.11 package-only scope amendment

- **Decision date:** 2026-10-04 (Europe/Moscow)
- **Authority:** the owner's explicit direction in the current Router UI
  `0.7.11` finalization task, recorded here for review; this is a new decision,
  not an assertion about approval or qualification in an earlier task.
- **Target release:** Router UI `0.7.11`, a package-only trust/update bridge.
- **Release goal:** qualify and freeze a private stable package candidate for
  a separately authorized owner-controlled physical-router canary.
- **Acceptance criterion closed:** resolve the declared deliverable set and
  qualification boundary before stable candidate freeze.
- **Why required:** the historical image and Factory requirements otherwise
  conflict with the owner's current package-only decision; silently omitting
  them or treating RC18 evidence as stable evidence would hide release gaps.
- **Product/runtime effect:** none. This amendment authorizes no new feature,
  functional change, hardware contact, or public publication.
- **Evidence to add:** exact integration ancestry, source and tree identities,
  source preflight and CI, full control census, independent reproducible IPKs,
  production signature verification, exact-byte VM matrices, and a frozen
  hardware handoff record.

## Canonical deliverables and explicit deferrals

The canonical `0.7.11` software payload is exactly these three project IPKs:

- `premier-router-core`
- `luci-app-premier-router`
- `premier-router-setup`

The distribution includes their signed feed, signed release manifests,
checksums, complete build/signing provenance, and ordinary-user installation,
supported-update, exact-rollback, and recovery guidance. It introduces no
additional project package category. Any installer or release metadata used
by these workflows must be bound to the same frozen source and evidence.

| Item | New decision | Reason and consequence | Next target |
|---|---|---|---|
| x86 firmware image publication | Deferred | `0.7.11` distributes the package bridge; no x86 image is a canonical stable asset or receives an image readiness claim | `0.8.0`, subject to its own gates |
| RD23 stock firmware image publication | Deferred | No stock image or stock Factory production readiness is claimed by this package release | `0.8.0`, subject to its own gates |
| RD23 ubootmod firmware image publication | Deferred | No ubootmod image or layout-specific readiness is claimed by this package release | `0.8.0`, subject to its independent gates |

A disposable VM image may be a documented test fixture without becoming a
release deliverable. Image/Factory artifacts must not be added later to the
same immutable `0.7.11` release. These deferrals change distribution scope,
not feature scope: the existing bridge-only non-goals remain unchanged.

## Qualification contract

Run exact-head source preflight and CI before final builds. Complete the
real-browser census of all 46 declared controls through the real authenticated
LuCI, RPC/ACL, and backend paths. Each control needs its expected state,
stable selector, exercised outcome or individually justified non-applicability,
backend result, restoration result, and retained browser/console evidence.
The former `42/46` result cannot be carried forward as completion.

Non-applicability must cite the governing contract and the exact control and
fixture state. A read-only caller must be proven unable to dispatch mutations
through both UI and backend ACL enforcement. An empty/no-peer fixture can
explain why a particular peer action cannot apply in that state; it cannot
waive that action in a supported configured state. Missing enrollment
credentials, peers, or test execution are limitations, not successful tests.
Where enrollment is an enabled supported workflow, its applicable GUI path
still requires evidence. No read-only or no-peer blanket exception is created
by this amendment.

The completed browser/VM matrix must cover updater success and failure
isolation; native and adopted Xray states and fail-closed states; persistent
device bypass/dnsmasq behavior; Tailscale stopped-daemon cold start; applicable
restart, stop, and logout controls; exact restoration/rollback; read-only
ACLs; and error-state UI refresh.

One build owner must build the three stable IPKs twice from clean independent
worktrees with pinned production inputs and require byte-for-byte equality.
Use the protected `production-2026-07` signing identity and derive its public
fingerprint, requiring `d055711acf1d9a5b`; a filename or environment key ID is
not proof. Private signing material must never appear in the repository,
artifacts, logs, or transcript.

On those exact signed stable bytes, complete the package-only VM matrix:
supported `0.7.10` to stable; RC18 to stable if the transition contract supports
it; every other declared supported baseline; same-version reinstall and
idempotence; reboot validation and commit; exact rollback; controlled
download, checksum, signature, compatibility, and storage failures;
configuration and init-state restoration; and post-authentication browser
smoke. Unsupported transitions must refuse before mutation. A required path
cannot be dropped merely because a convenient starting fixture is absent.

Evidence must remain immutable and bind source commit/tree, clean-build
proof, build/staging scripts, toolchain and feed lock, both build outputs,
manifest/checksum/signature hashes, package sizes/hashes, derived signing
fingerprint, workflow/run IDs, test starting states, results, and limitations.
Changed bytes invalidate affected downstream evidence. Verification labels
must reflect the actual executed gate.

## Hardware and publication stop boundary

Before any public stable publication, one owner-controlled physical router
must pass the package canary using the exact staged stable bytes. Record its
authorized identity and starting state, management/recovery path and backup,
package update, actual network/application behavior, reboot validation and
commit, configuration/init persistence, exact rollback/restoration, and the
applicable controlled failure/recovery checks. VM success does not satisfy
this gate. No rebuild or re-sign may occur between VM qualification and the
hardware canary without invalidating the affected evidence and repeating it.

The current task expressly forbids contact with any physical router, creating
or pushing the final tag, creating or publishing a GitHub Release, enabling
normal discovery, and enabling GitHub Latest. Public publication and rollout
remain separately authorized, with the eventual release commit contained in
`origin/main`. The first public stable rollout remains manual-first.

The task ends with a concise `READY_FOR_HARDWARE.md`: GO/NO-GO; exact source
commit/tree; the three IPK filenames, sizes, and SHA-256 values; signed
manifest/checksum identities; derived public signing fingerprint; exact
CI/workflow IDs; completed VM/browser matrices; and the remaining physical
canary checklist. GO means ready for that separately authorized canary only.
It must state that the qualified bytes are frozen and must be used unchanged.
If readiness is not unequivocal, report NO-GO and only the remaining blockers;
do not infer completion from historical results or planned tests.
